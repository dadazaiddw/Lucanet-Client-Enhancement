**F01：后缀补全删除业务表达式中的竖线**

位置：[JavaIntelligence.java:659](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaIntelligence.java:659>)。

模板先把原表达式拼进字符串，再用 `indexOf('|')` 查找光标，用 `replace("|", "")` 删除占位符。它无法区分占位符与用户输入中的逻辑或、按位或、字符串内容。

```java
// 输入后选择 sout 后缀
"a|b".sout
// 实际生成
System.out.println("ab");

// 输入后选择 not 后缀
(a || b).not
// 实际生成
!((a  b))
```

第一个例子仍可编译，却改变实际输出；第二个例子直接编译失败，光标位置也计算错误。建议把插入文本和光标位置分别保存，禁止对拼入业务表达式后的字符串做全局占位符删除。修复前，含竖线的表达式手动编写对应代码。

证据：[JDK 21](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/docs/evidence/audit-2026-11-21/generation-jdk21.txt>)、[JDK 17](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/docs/evidence/audit-2026-11-21/generation-jdk17.txt>) 中的 `BooleanOrPostfix` 和 `StringPipePostfix`。

**F02：保存后类型含义改变，却仍标记为原生兼容**

位置：[CustomJavaParts.java:179](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/CustomJavaParts.java:179>)。

复现前提：在完整源码中移除模板自带的显式 `ln.source.api.Date` 导入，只保留 `java.util.*`，例如粘贴普通 Java 源码时：

```java
package com.lucanet.common.dom.script.rt;
import java.util.*;
public class WildcardDate {
    public String value() { return Date.class.getName(); }
}
```

保存前，独立编译执行得到 `java.util.Date`。同步时不能删除的原生导入重新加入 `import ln.source.api.Date;`；保存后的实际源码执行得到 `ln.source.api.Date`。探针输出 `synced=true warning=false ... same=false`。

`importConflict()` 跳过所有 `.*` 导入，只检查显式同名导入，因此没有识别这一变化。当前同步类的增强客户端也使用原生生成源码，故这是**源码编辑/诊断与保存后执行之间的变化**，不应描述成增强端与服务器一定执行不同代码。

建议对待同步源与原生投影做类型绑定一致性检查，或保守识别内置导入引入的名称遮蔽；不一致时保留完整源码并明确提示原因。修复前，预期使用 JDK Date 的位置使用 `java.util.Date` 全限定名。仅增加显式 `import java.util.Date` 会触发现有内置导入冲突限制，不能当作服务器兼容方案。

证据：[原生投影对比](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/docs/evidence/audit-2026-11-21/native-projection.txt>) 中两个版本的 `WildcardDate`；`NoWildcardImports` 是全限定名正常的对照。

**F03：原生修改回读丢失声明注释，再保存后覆盖原文**

位置：[CustomJavaModel.java:189](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/CustomJavaModel.java:189>)、[CustomJavaParts.java:222](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/CustomJavaParts.java:222>)。

步骤：增强端保存一个带类 Javadoc、字段解释和方法 Javadoc 的普通类；原生端只修改某个方法体；增强端回读。`Version` 检测到原生部件变化后，整份源代码切换为 `Snapshot.source()`。该重建器只输出导入、字段和方法，声明上的注释没有映射或合并逻辑。

实测三类声明注释全部消失，方法体内注释仍保留，状态没有警告。此时原始完整源码暂时仍在节点属性中；把回读后的源码再次保存，原注释也会从存储源码中消失。因此不能仅视为显示问题。

建议基于上次保存的完整源码和部件基线，对原生修改做 AST 级局部合并；无法安全合并时保留原文并提示。至少在将有注释的完整源码整体替换前提供保护。修复前保留完整源码副本，并在原生修改回读后检查声明注释。

证据：[原生投影对比](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/docs/evidence/audit-2026-11-21/native-projection.txt>) 中 `CommentRoundTrip` 与 `originalCommentsRetainedAfterResave=false`。

**F04：导包整理会引入静态嵌套类型歧义**

位置：[JavaIntelligence.java:677](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaIntelligence.java:677>)、[JavaIntelligence.java:683](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaIntelligence.java:683>)。

```java
import static java.awt.Desktop.*;
import javax.swing.Action;
import javax.swing.JButton;
class Demo { Action action; JButton button; }
```

原文可编译。整理后两个显式导入合为 `javax.swing.*`，静态导入保持不变；`Action` 同时匹配 `Desktop.Action` 和 `javax.swing.Action`，编译报 `compiler.err.ref.ambiguous`。检查消歧的代码仅列举非静态通配包，遗漏了静态导入也能提供类型这一情形。完整源码手动整理和调用该分析器的自动整理均涉及此路径。

建议纳入静态导入中的可访问嵌套类型，或在应用整理结果前重新分析，保证既有类型绑定不变。暂时把冲突位置写成全限定名；依赖显式导入消歧时避免触发自动通配合并。

证据：两个 `generation-jdk*.txt` 的 `StaticImportConflict compiledBefore=true compiledAfter=false`，由独立 javac 和编辑器诊断分别确认。

**F05：泛型重写生成了错误的类型变量绑定**

位置：[JavaTypeActions.java:213](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaTypeActions.java:213>)。

```java
class Base<X> {
    public <T> X convert(T x) { return null; }
}
class Demo<T> extends Base<T> { }
```

原文可编译。在 Demo 中重写 convert，生成 `public <T> T convert(T x)`：方法自己的 T 遮蔽了类的 T，返回类型不再对应父类的 X。编译出现不兼容返回类型等错误。

正确结果需要为方法类型参数选择不冲突的名字，例如 `public <U> T convert(U x)`，并同步替换其参数、边界及异常类型引用。建议基于类型变量元素身份进行重命名，不能只替换显示字符串。修复前手动调整生成签名。

证据：两个 `generation-jdk*.txt` 中 `GenericOverrideShadow compiledBefore=true ... compiled=false`。

**F06：枚举生成方法时没有处理常量区边界**

位置：[JavaTypeActions.java:105](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaTypeActions.java:105>)、[JavaMemberGeneration.java:124](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaMemberGeneration.java:124>)。

对 `enum Demo { A, B }` 在尾部使用 Ctrl+O 重写 toString，生成器没有补上常量列表后的 `;`。即便源码是 `enum Demo { A, B; }`，当光标在 A 之前时，生成器也可能把方法放入枚举常量之前。这两种原文均合法，生成后均不能编译。

建议为枚举设置独立插入规则：普通方法必须位于常量区及分号之后，缺少分号时将它与生成方法作为一个撤销事务加入。暂时先写 `;`，并将光标放在其后再生成。

证据：`EnumWithoutSeparator`、`EnumBeforeConstant` 均失败；`EnumWithSeparator` 在分号后生成正常。

**F07：合法的多顶层类型源码被错误诊断为文件名不匹配**

位置：[JavaIntelligence.java:361](<D:/File/Codex/Lucanet/增强插件/Lucanet-Client-Enhancement/src/main/java/cn/lucanet/enhancement/exit/JavaIntelligence.java:361>)。

`class Helper {} public class Primary {}` 本身可以作为 Primary.java 编译，保存解析器也正确选中 Primary。编码辅助的 `sourceName()` 却正则选取第一个类型 Helper，把整份源码当作 Helper.java 分析，报 `compiler.err.class.public.should.be.in.file`。

这是辅助诊断误报；没有证据表明它会阻止原生编译。建议使用语法树优先选择 public 顶层类型，与保存解析器一致。暂时将 public 主类型放在辅助类型前面。

证据：`PublicAfterHelper independentCompiler=true` 同时出现上述诊断码。多个顶层类型原本就属于只在增强端使用的定义，其服务器兼容限制与本误报是不同问题。
